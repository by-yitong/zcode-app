# ZCode 网页端逆向分析

> 数据源:zcode.z.ai 网页客户端 **主 JS bundle** (`/remote/v4/assets/index-BdDWMeL9.js`, 4.5MB, app_version 3.6.4)
> 静态分析于 2026-07-31。所有结论均来自网页端 bundle, 不涉及本地桌面端。
> 配合阅读: `API协议规格.md` (WS 握手/认证/帧格式实测)、`API逆向分析.md` (URL 认证两条路径)。

---

## 一、网页端架构

网页端 (`https://zcode.z.ai/remote/v4`) 是一个 **Vite 打包的单页瘦客户端**:

```
入口  /remote/v4/assets/index-BdDWMeL9.js   (主代码, 含全部业务逻辑)
样式  /remote/v4/assets/index-CPFcCvO2.css
懒加载 chunks  /remote/v4/assets/<name>-<hash>.js   (按需: 代码高亮语言包、图表组件、架构图等)
```

- **技术栈**: React + Zustand (状态) + xterm.js (终端渲染) + Zod (协议 schema 校验)。
- **角色**: 瘦客户端。所有 AI 推理 / 文件操作 / 终端 / 定时任务执行都在远程环境完成, 网页端只发指令 + 渲染结果。
- **通信**: WebSocket → relay 中继 → RPC bridge。**无 REST 业务 API** (仅认证/凭据走少量 HTTP)。

网页端的能力边界 = 移动端 app 能复刻的天花板。下文逐项列出。

## 二、连接与传输层

### 2.1 两条 WebSocket 入口 (bundle 实测)

网页端 bundle 里有两处 `new WebSocket`:

| 用途 | URL 模式 | 说明 |
|------|----------|------|
| **远程控制主连接** | `${relayOrigin/ws/wss}/ws/remote-control/window/${token}` | token = remoteControlToken (REST 路径, 见 API逆向分析.md §7.2)。这是网页 `/remote/v4` 实际用的连接。 |
| **通用 WS 工具** | `new WebSocket(e)` (封装函数 V0t) | 辅助/探测用途。 |

> 注: app 当前用的是 `/remote/v3` 的 sid/hash/mid + 4 步 HMAC 路径 (API协议规格.md §二), 连 `wss://zcode.z.ai/ws`, 用**裸 rpc-frame** (v3 协议, 能正常工作)。
> 网页 `/remote/v4` 走 token 直连 `/ws/remote-control/window/{token}`, 用**v4 logical-frame 协议** (见 §2.4)。
> ⚠️ **v3 与 v4 的 RPC 帧格式不同!** v3 发 `{zcode_type:'rpc-frame', dataBase64:<[100,id,ch,method]>}`; v4 在外层仍是 rpc-frame, 但 dataBase64 内编码的是 `v4/conversation/frame` 方法调用 + logical frame 封装 (见 §2.4)。用 v3 裸帧连 v4 端点会触发 `rpc-transport-fault` (实测确认)。


### 2.2 业务帧类型 (zcode_type, bundle 实测)

网页端用反引号模板字符串构造帧, 完整枚举:

| zcode_type | 方向 | 用途 |
|------------|------|------|
| `bootstrap-request` | → | 启动拉取工作区+任务 |
| `workspace-list-request` | → | 刷新工作区列表 |
| `workspace-bridge-open` | → | 打开 bridge (带 `recoveryId` 恢复字段) |
| `workspace-reconnect-request` | → | 断线重连请求 |
| `rpc-frame` | ↔ | RPC 请求/响应/事件 (核心) |
| `rpc-frame-ack` | → | 帧确认 (流量控制) |
| `mobile-view-state-update` | → | 上报当前视图 (fire-and-forget) |
| `mobile-diagnostic` | → | 移动端诊断 |
| `platform-request` | → | 平台级 RPC |

> 帧结构见 API协议规格.md §三、§四 (JSON 包裹 `payload` + `requestId` 配对, 与网页端一致)。

### 2.3 RPC 帧 (rpc-frame)

二进制自描述序列化, header = `[type, requestId, channel, method]`:

| type | 名称 | 说明 |
|------|------|------|
| 100 | PromiseRequest | 客户端调用 |
| 102 | EventListen | 客户端订阅事件流 |
| 200 | Init | bridge 就绪推送 |
| 201 | OK | 成功响应 |
| 202/203 | Error | 错误响应 |
| 204 | EventFire | 事件推送 |

序列化器 `rm(writer, value)` 支持: Undefined/String/Bytes/Array/JSON Object/Int (varint), 与 `rpc_codec.dart` 一致。

> §2.3 描述的是 **v3 裸 rpc-frame 协议** (app 当前使用, 能工作)。下面 §2.4 是 **v4 协议**, 二者不同。

### 2.4 V4 协议 (网页端 `/remote/v4` 实际使用) ★ 抓包实测

> 通过 headless Chrome + CDP `Network.webSocketFrameSent/Received` 抓取网页端真实流量 (173 帧), 以下为实测结果, 推翻了早期"logical-frame 封装"的静态推断。

#### 核心结论: v4 与 v3 的 RPC 内容完全相同, 仅 rpc-frame 外层封装不同

抓包解码确认: v4 的 `dataBase64` 内部仍是 **二进制 `[type, id, channel, method] + args`** (与 v3 `rpc_codec.dart` 同源)。channel/method 名与 v3 **完全一致** (实测):

```
setting.get, broadcast.onMessage, oauth.restoreCachedSession,
model-provider.getAllCached / getDisplayOrder,
zcode-agent.helloConversationV4 / onDynamicConversationFrame / onDynamicSessionsIndexFrame / onAgentRuntimeRestarted,
zcode-task.listPinnedTaskIds / listArchivedTasks / listTasks
```

**没有 `v4/conversation/frame` 这个统一方法** (早期静态推断错误)。业务方法名 (helloConversationV4 等) 直接作为 RPC method, channel 不变。

#### v4 rpc-frame 外层结构 (与 v3 的唯一差异) ★

抓包真实帧:
```json
{
  "zcode_type": "rpc-frame",
  "bridgeSessionId": "bridge-4954ec83-0d93-4932-b92c-a3f5745d54db",
  "bridgeGeneration": 1,
  "seq": 2,
  "messageSeq": 2,
  "fragmentIndex": 0,
  "fragmentCount": 1,
  "messageBytes": 22,
  "checksum": { "algorithm": "crc32", "value": "e380ade4" },
  "dataBase64": "<二进制 [100,id,channel,method]+args 的 base64>"
}
```

**v4 比 v3 多的字段** (缺任一项 host 静默丢弃, 不报错):
| 字段 | 值 | 说明 |
|------|-----|------|
| `messageSeq` | 递增整数 | 逻辑消息序号 (与 seq 区分) |
| `fragmentIndex` | 0 | 当前分片序号 |
| `fragmentCount` | 1 | 总分片数 (整帧=1) |
| `messageBytes` | dataBase64 解码后字节数 | 例如 22 |
| `checksum` | `{algorithm:"crc32", value:"<hex8>"}` | **CRC32 校验, 对 dataBase64 解码后的字节** |

> ⚠️ **checksum 是关键**: host 用 CRC32 校验 `dataBase64` 解码后的字节, 不匹配则静默丢弃。早期探针不加这些字段 → 不 fault (因有 recoveryId) 但 host 静默不回。

#### v3 → v4 的实际改动 (app 若要支持 v4)

1. rpc-frame 外层加 `messageSeq` (递增) / `fragmentIndex:0` / `fragmentCount:1` / `messageBytes` (dataBase64 解码字节数)。
2. 算 **CRC32** (对 dataBase64 解码后的 bytes), 填 `checksum:{algorithm:"crc32", value:"<8位hex>"}`。
3. 时序: bridge-open → bridge-ready → RPC Init(200) → 才发业务 RPC。
4. channel/method/二进制编码逻辑**完全不变** (v3 代码可复用)。

#### 连接 (与 v3 相同)

`wss://zcode.z.ai/ws?mid={mid}` + 4 步 HMAC 握手 (sid/hash/mid/cookie)。v4 与 v3 走同一 WS, 仅 bridge 后 RPC 封装不同。

#### 静态逆向的 `v4/conversation/frame` 是什么

bundle 里的 `bOe`/`JE`/logical-frame 是**帧大小预算 + 大帧分片协议** (`bOe` 计算三种传输格式最大字节; `JE` 是分片重组 schema)。仅当单消息超阈值时才走分片 (kind:"fragment"); 普通业务帧是单物理帧 (fragmentCount:1), 不涉及 conversation topic。`eD(topic)` 的 conversation topic 校验是**订阅事件流** (`onDynamicConversationFrame`) 的参数, 不是每个 RPC 都要。

### 5.4 MCP 服务器 (ZCodeAgent / McpSync)

> MCP 是**配置文件驱动**的。网页端用 Zustand store 管理, 通过 `addMcpServer`/`updateMcpServer`/`deleteMcpServer` 修改本地配置, 再 `saveConfig` 同步。

**配置结构** (bundle 实测, localStorage key `zcode-mcp-config` / `zcode-mcp-deleted-preload`):
```typescript
{
  mcp:          { mcpServers: {} },          // 标准 MCP
  zcodeagentmcp:{ mcpServers: {}, projects: {} }, // ZCode agent MCP
  claudeclimcp: { mcpServers: {}, projects: {} },
  geminiclimcp: { mcpServers: {}, projects: {} },
  codexclimcp:  { mcpServers: {}, projects: {} },
}
```

| store 方法 | 用途 |
|-----------|------|
| `addMcpServer(name, config)` | 添加服务器 |
| `updateMcpServer(name, config)` | 更新 |
| `deleteMcpServer(name)` | 删除 |
| `addZCodeAgentMcpServer` / `updateZCodeAgentMcpServer` / `deleteZCodeAgentMcpServer` | ZCode agent 域 MCP |

### 5.5 终端 (Terminal channel) ★

> 终端**确实走 RPC bridge**, 不是纯本地。网页端用 xterm.js 本地渲染 + 远程 PTY 数据流。

**数据流** (bundle 实测):
```
用户键入 → xterm.onData(data) → j.write({id: terminalId, data})   // 发到远程
远程输出 → onDynamicData(terminalId)(data) → xterm.write(decoded)  // 写入本地
```

|------|------|------|
| `terminalService.resize` | 调整终端尺寸 | `{id, cols, rows}` |
| `terminalService.write` (推测) | 写入数据 | `{id, data}` |
| `systemService.listIntegratedTerminalShells` | 列可用 shell | — |
| 创建终端会话 | (走 bridge 动态通道) | `{terminalTabId, ...}` |

事件: `onDynamicData(id)` (输出流), `onDynamicExit(id)` (终端退出)。

### 7.2 动态验证的死结 (实测确认)

配套探针 `tool/probe_webremote.dart` 多次实测, 现象稳定:

```
auth_ack pair_status=matched        ← 认证通过 ✅
bootstrap 7 workspaces              ← 拉取工作区 ✅
★ bridge ready                       ← 抢到 bridge ✅
(1.2 秒后)
!! bridge-degraded (被抢占)          ← RPC 帧被丢 ❌
```

**bridge ready 后 1.2 秒必被抢占**。即使 app/网页端都不连, 也持续被抢。根因: **同一 sid 同时只允许一个 bridge**, 而本机有进程持续维持该 bridge (见下方排查)。

排查到连 relay (`124.160.144.209`) 的进程:
- `zcode-cli` pid 26874 — 承载当前 CLI 会话本身 (探针的运行环境)
- `zcode` NetworkService pid 26681 — 桌面端 ZCode 网络服务

**结论**: 在"探针和桌面端共用同一 sid/运行环境"的条件下, 无法独占 bridge 做 RPC 探测。动态验证需在**独立的运行环境 + 独占 bridge 的窗口**进行 (如: 另一台机器跑探针, 或桌面端彻底退出远程控制)。
